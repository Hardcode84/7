# GFX950 Matmul Profiles

## Repro Preflight

After branch switch or rebase, rebuild every tool used by matmul calibration:

```bash
cmake --build build --target wave-opt wave-translate WavePythonModules -j "$(nproc)"
```

`wave-matmul-calibrate` invokes `build/bin/wave-translate` for HSACO and ISA
generation. Rebuilding only `wave-opt` can leave stale codegen in perf runs.

Large checked runs compute a CPU reference; use `--no-check` for perf sweeps
and keep correctness checks to smaller smoke shapes.

`wave-sim-report` runs are capped to 32 loop trips by default to keep large-K
reports responsive. Pass `--sim-trip-count=-1` when a full-trip simulator
report is required.

Perf ASM goldens for the f16 and MXFP4 profiles are generated by
`test/PerfGolden/test_*.py` through `--emit-asm`. Do not add frozen Wave MLIR
inputs for these profiles.

Ordinary matmul `automatic` output is row-major. hipBLASLt-style profiles
select column-major; AITER profiles select row-major. `tile-packed` is an
explicit compatibility/debug layout, not a named profile ABI.

Recorded f16-16-wave and standard MXFP4 measurements below predate direct
final-layout stores and used tile-packed output. Keep them as historical
scheduler evidence; remeasure current column-major profiles before comparing
throughput.

## AITER MXFP4 Input Layout

`--mxfp4-input-layout=aiter` consumes the AITER preshuffle ABI:

- A: raw packed FP4, `[M, K/2]` bytes.
- B: `shuffle_mxfp4_b_aiter` output.
- A/B scales: `shuffle_mxfp4_scales_aiter` output, row count padded to a
  multiple of 256 and K32 group count padded to a multiple of eight.

A stays on the global-to-LDS DMA path. B fragments and packed scale dwords load
directly from their preshuffled global layouts. Kernel stores F16 row-major
output directly.

Runtime integration covers all 16 MXFP4 codes and four scale values in each
input buffer. CPU reference uses independent canonical inputs and compares
every row-major device result.

Five named profiles cover the AITER benchmark matrix:

| Profile | CTA | Wave tiles | K tiles | Shapes |
|---|---:|---:|---:|---|
| `gfx950-mxfp4-aiter-32x128` | 32x128 | 2x2 | 2 | 256x4096x4096 |
| `gfx950-mxfp4-aiter-64x128` | 64x128 | 4x2 | 2 | 256x8192x4096, 512x4096x4096 |
| `gfx950-mxfp4-aiter-128x128` | 128x128 | 8x2 | 2 | 512x8192x4096 |
| `gfx950-mxfp4-aiter-128x256` | 128x256 | 8x4 | 4 | 2048x4096x8192 |
| `gfx950-mxfp4-aiter-256x256` | 256x256 | 16x4 | 4 | 2048x8192x4096, 2048x8192x8192 |

`per_launch_us` and sweep TFLOP/s cover GEMM. Host copy and CPU reference stay
outside timing. `mxfp4-aiter` and default `all` each select the five profiles
once in table order. Matching-gfx950 device results are not recorded for this
integrated pipeline; default inclusion is not a performance claim.

Run the AITER matrix with:

```bash
python tools/wave-matmul-calibrate/wave-matmul-perf-sweep.py \
  --kernels=mxfp4-aiter --hip-visible-devices=0 \
  --iters=200 --warmup=25 --repeats=9
```

Scheduler implication:

- Current `lower-before-schedule.mlir` already has
  `ds_read_b64_tr_b8x6 -> MFMAx32 -> s_barrier`; machine scheduling preserved
  that bad shape. The barrier placement bug is not created solely by the final
  greedy scheduler.
- Moving the full scale-read barrier before the independent MFMA group
  reproduces most of the missing performance. See the manual split-barrier
  experiment below.
- The scheduler/model needs to price barrier arrival skew. A barrier that joins
  memory producers for a following compute group should not sit behind partial
  consumers of those producers unless the model can prove the later barrier is
  cheaper.
- The previous VMEM-producer-window conclusion was an attribution artifact from
  combined wait counters. Track drained counter class separately from pending
  counter class when reading ATT window summaries.

- Split arrive/wait semantics would help this kernel. The early hardware
  proxy recovers `8079` cycles, and the software split probe recovers `6415`.

Key result: largest ATT barrier is not automatically the best split target.
8-wave ordinal 3 has the largest standalone stall, but ordinal 2 wins because
its arrive is hidden under a pure MFMA window. The corrected disabled baseline
changes the 4-wave conclusion: split barriers regress 4-wave and only help
8-wave in this sweep. Stacking split barriers gives back overhead and can
wedge.

Final scheduler rule:

- Pull `barrier_arrive` only over a real independent window.
- Reject if the pull crosses same-counter memory producers.
- Accept either a compute-only window (`>=16` VALU/MFMA/trans ops) or a
  memory-only window (`>=4` memory ops). Reject mixed compute+memory windows.
- Keep at most one eager arrive window per straight-line greedy region.
- If arrive was not pulled, schedule its matching wait immediately; later
  cleanup folds the adjacent pair back to `s_barrier`.

## `gfx950-f16-256x256-16wave-persistent`

Opt-in 4-producer/12-consumer experiment. Four persistent waves issue
direct-to-LDS traffic; twelve waves compute 64x80 or 64x96 output strips.
Three LDS stages use 98336 dynamic bytes. Monotonic returning-atomic mailboxes
replace steady-state barriers.

```bash
python tools/wave-matmul-calibrate/wave-matmul-perf-sweep.py \
  --kernels=f16-persistent,f16-persistent-pipelined,f16-persistent-pipelined-k64 \
  --m=8192 --n=8192 --k-values=8192
```

`--extra-calibrator-arg=--persistent-completion=waitcnt` selects the blocking
control. Default is `IB_STS.VM_CNT` polling with `s_sleep 1`.

`gfx950-f16-256x256-16wave-persistent-pipelined` buffers B fragments and
publishes stage completion before its final MFMA group. Its random
8192x8192x8192 median is 964.6 TFLOP/s.

`gfx950-f16-256x256-16wave-persistent-pipelined-k64` batches two K32 slices per
mailbox generation. It uses two 64 KiB stages, 131104 dynamic LDS bytes, and
a mid-batch poll plus blocking final VMEM completion. K must be a multiple of
64 and at least 192. Its random 8192x8192x8192 median is 1073.2 TFLOP/s, 11.3%
above pipelined K32 and 27.4% below the existing 4-wave kernel. HPL medians are
939.4 TFLOP/s for K64 and 856.2 TFLOP/s for K32.

All persistent profiles stay out of `all`. See
[asymmetric persistent-wave GEMM](Gfx950AsymmetricPersistentWaveGemmDesign.md)
for protocol, correctness, ATT, and PMC results.

```bash
  --dynamic-lds 135168 --iters 1 --warmup 0 --seed 0 --no-check \
  <hsaco> wmma_f16_matmul_tiled
```

ATT collection:

- `rocprofv3 --att` is the preferred frontend when it configures cleanly.
- If it fails during `rocprofiler_configure_device_thread_trace_service`, use
  the ROCprofiler SDK thread-trace API directly. The SDK sample in
  `rocprofiler-sdk/samples/thread_trace` already decodes per-PC instruction
  duration.
- Start the thread-trace context on the HIP launch callback and stop it on
  `hipEventSynchronize`/`hipDeviceSynchronize` exit. Stopping only at process
  finalization can leave an empty trace because shader data is not flushed in
  time.
- Trace one CU/SE for comparable runs, e.g. `target_cu=1`,
  `shader_engine_mask=1`, `buffer_size=268435456`.

ATT decoder `duration` is not global-memory completion latency. For gfx10+ it
is stall plus execution time for the instruction. A high duration on
`buffer_load_dwordx4 ... lds` means issue-side stall or pipe/backpressure while
issuing the async global-to-LDS load. The data can still complete later, and the
real drain can appear at a later wait or barrier.
